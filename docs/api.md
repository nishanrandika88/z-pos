# API Specification

Z-POS primarily uses Supabase table APIs for CRUD and PostgreSQL RPC functions for transactional workflows.

## Auth

### Login

```ts
supabase.auth.signInWithPassword({ email, password })
```

Validation:

- `email`: valid email.
- `password`: required.

Errors:

- `401`: invalid credentials.
- `423`: account locked.
- `429`: rate limit exceeded.

### Forgot Password

```ts
supabase.auth.resetPasswordForEmail(email, { redirectTo })
```

## Catalog

### List Categories

`GET /rest/v1/categories?select=id,name,active,created_at,updated_at`

Response:

```json
[{ "id": "uuid", "name": "Juices", "active": true }]
```

### Create Item

`POST /rest/v1/items`

Request:

```json
{
  "item_code": "ORG-001",
  "barcode": "4790000000012",
  "item_name": "Orange Juice",
  "selling_price": 850,
  "category_id": "uuid",
  "availability": true,
  "active": true
}
```

Validation:

- `item_code`: unique per branch.
- `barcode`: unique per branch when present.
- `selling_price`: greater than zero.

## Discounts

### Create Discount

`POST /rest/v1/discounts`

Request:

```json
{
  "name": "Fresh Juice Promo",
  "percentage": 10,
  "applicable_type": "CATEGORY",
  "applicable_id": "uuid",
  "active": true
}
```

Constraint:

- one active discount per item/category target.

## POS

### Search Items

`GET /rest/v1/items?or=(item_code.ilike.*term*,barcode.eq.term,item_name.ilike.*term*)`

### Create Order

`POST /rpc/create_pos_order`

Request:

```json
{
  "order_payload": {
    "lines": [
      {
        "item": {
          "id": "uuid",
          "itemCode": "ORG-001",
          "itemName": "Orange Juice",
          "sellingPrice": 850
        },
        "quantity": 2,
        "automaticDiscount": 170,
        "lineTotal": 1530
      }
    ],
    "totals": {
      "subtotal": 1700,
      "automaticDiscount": 170,
      "manualDiscount": 0,
      "tax": 0,
      "grandTotal": 1530
    },
    "payment": {
      "method": "CASH",
      "amountTendered": 2000,
      "balanceReturned": 470
    }
  }
}
```

Response:

```json
"order-uuid"
```

Rules:

- Generate order number on server.
- Save order, order items, payment, and audit event in one transaction.
- Print only after this RPC succeeds.

## Reports

Recommended RPC/view endpoints:

- `daily_sales_report(start_date, end_date)`
- `monthly_sales_report(year)`
- `item_sales_report(start_date, end_date)`
- `category_sales_report(start_date, end_date)`
- `discount_usage_report(start_date, end_date)`
- `cashier_performance_report(start_date, end_date)`

Export formats:

- CSV: generated client-side for small reports.
- Excel/PDF: generated by Edge Function for production scale.

## Error Handling

Canonical shape:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Selling price must be greater than zero",
  "details": {}
}
```

Important codes:

- `UNAUTHORIZED`
- `FORBIDDEN`
- `VALIDATION_ERROR`
- `DUPLICATE_ITEM_CODE`
- `DUPLICATE_BARCODE`
- `ORDER_SYNC_CONFLICT`
- `PAYMENT_CAPTURE_FAILED`

## Expenses

Transactional RPCs:

- `create_expense(expense_payload)`: idempotent by branch/client request UUID; recalculates lines and requires balanced funding.
- `update_expense(target_expense_id, expected_version, expense_payload)`: edits draft/pending records and rejects stale versions.
- `approve_expense(target_expense_id, expected_version)`: approves and posts linked inventory exactly once.
- `mark_expense_paid(target_expense_id, expected_version)`: finalizes payment after approval.
- `void_expense(target_expense_id, expected_version, reason)`: records the reason and reverses posted stock when safe.
- `reopen_void_expense(target_expense_id, expected_version)`: admin-only recovery that returns a voided record to draft while retaining its audited purchase/reversal stock history.
- `record_expense_reimbursement(...)`: row-locks personal funding and prevents over-reimbursement.
- `review_expense_receipt(target_receipt_id, corrected_payload)`: stores audited corrections without creating financial data.

Master-data and list reads use the Supabase table API under RLS. Receipt extraction uses the authenticated `process-expense-receipt` Edge Function; provider keys are Edge Function secrets, never frontend environment variables.

Expense categories expose a stable `form_type` (`GENERAL`, `SALARY`, `RENT`, `UTILITY`, `INVENTORY_PURCHASE`, or `EQUIPMENT_REPAIR`) in addition to their reporting `kind`. RPC validation uses this stable type rather than the editable category name. Rent, utility, and equipment fields are stored in `expense_category_details`; salary records may reference either a standalone `employees` record, a login `profile`, or a manual name snapshot. Personal funding keeps the payer name snapshot and, when selected, the linked employee/profile identity used as the reimbursement recipient.
